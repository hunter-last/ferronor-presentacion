integridad referencial

RESTRICT protege, CASCADE acompaña

Regla de arquitectura del proyecto: ON DELETE RESTRICT por defecto, CASCADE reservado a tablas de detalle puro.

RESTRICT

categoria ← producto

producto.id_categoria REFERENCES categoria(id_categoria) ON DELETE RESTRICT

Si un producto todavía apunta a esa categoría, PostgreSQL bloquea el borrado. Un padre en uso no puede desaparecer.

CASCADE

venta → detalle_venta

detalle_venta.id_venta REFERENCES venta(id_venta) ON DELETE CASCADE

El detalle no tiene ciclo de vida propio: depende por completo de su cabecera. Si la venta se va, sus líneas se van con ella.

ARQUITECTURA.md lo fija como política explícita: ON UPDATE CASCADE en todas las FK, ON DELETE CASCADE únicamente en detalle_venta, detalle_compra, detalle_orden_compra, detalle_asiento y rol_permiso. Todo lo demás, RESTRICT.

restricciones CHECK

Una línea, un solo lado

El CHECK de detalle_asiento protege cada línea contable — no el asiento completo.

sql/07_contabilidad.sql
CREATE TABLE detalle_asiento ( ... debe NUMERIC(12,2) NOT NULL DEFAULT 0 CHECK (debe >= 0), haber NUMERIC(12,2) NOT NULL DEFAULT 0 CHECK (haber >= 0), CHECK ((debe > 0 AND haber = 0) OR (haber > 0 AND debe = 0)) );

Cada fila cae en el Debe o en el Haber — nunca en ambos, nunca en ninguno. Pero esto valida una línea a la vez. No garantiza que el asiento completo cuadre (que Σdebe = Σhaber): eso lo arma la lógica que construye el asiento, del lado de contabilidad/logica en Java.

venta / compra
CHECK (total = subtotal + igv)
cuenta_cobrar / cuenta_pagar
CHECK (saldo_pendiente = monto_total - monto_cobrado)

La integridad numérica no vive solo en contabilidad: el mismo principio se repite en ventas, compras y cuentas por cobrar/pagar.

consultas relacionadas

Un query, no cien

Los históricos de Compras y Ventas traen sus datos relacionados en una sola consulta con JOIN.

CompraDAOImpl.consultarHistorial() — fragmento simplificado
SELECT c.*, p.razon_social, fp.nombre, u.nombres FROM compra c JOIN proveedor p ON p.id_proveedor = c.id_proveedor JOIN forma_pago fp ON fp.id_forma_pago = c.id_forma_pago JOIN usuario u ON u.id_usuario = c.id_usuario

VentaDAOImpl.consultarHistorial() hace lo mismo con cliente, forma_pago y usuario, y agrega LEFT JOIN comprobante / LEFT JOIN tipo_comprobante — LEFT porque una venta puede existir todavía sin comprobante emitido.

reporte central

El Balance de Comprobación

Un reporte derivado: se calcula al vuelo con una agregación, nunca se guarda como tabla.

BalanceComprobacionDAOImpl.obtenerAgregadoPorCuenta(hasta)
SELECT pc.id_cuenta, pc.codigo, pc.nombre_cuenta, COALESCE(SUM(da.debe),0) AS total_debe, COALESCE(SUM(da.haber),0) AS total_haber FROM plan_cuenta pc JOIN detalle_asiento da ON da.id_cuenta = pc.id_cuenta JOIN asiento_contable a ON da.id_asiento = a.id_asiento WHERE a.estado = 'ACTIVO' AND a.fecha < ? GROUP BY pc.id_cuenta, pc.codigo, pc.nombre_cuenta ORDER BY pc.codigo

JOIN encadenado
plan_cuenta → detalle_asiento → asiento_contable, para llegar del catálogo contable al movimiento real.

Filtros del corte
estado = 'ACTIVO' excluye asientos anulados; fecha < ? define el "hasta" del balance.

El propio DAO deja el porqué por escrito: se usa JOIN y no LEFT JOIN a propósito, porque el balance solo debe mostrar cuentas con movimiento real — no el catálogo completo.

Decisión de arquitectura: el Balance de Comprobación —como el Kardex, el Libro Diario, el Libro Mayor y el Estado de Resultados— nunca es una tabla persistente. Siempre se recalcula.

rendimiento

Seis índices, seis razones

sql/09_indices.sql — nada se indexa "por si acaso".

1 idx_movimiento_producto_fecha
ON movimiento_inventario(id_producto, fecha) Kardex de un producto acotado a un rango de fechas.
2 idx_movimiento_fecha
ON movimiento_inventario(fecha) Movimientos de inventario filtrados por período, sin fijar producto.
3 idx_movimiento_origen
ON movimiento_inventario(origen) Filtrar por tipo de origen: COMPRA, VENTA, AJUSTE, DEVOLUCIÓN.
4 idx_ajuste_producto
ON ajuste_inventario(id_producto) Historial de ajustes de un producto puntual.
5 idx_cuenta_pagar_vencimiento parcial
ON cuenta_pagar(fecha_vencimiento) WHERE estado = 'PENDIENTE' Solo indexa lo que todavía puede vencer — las cuentas PAGADA o VENCIDA no ocupan espacio en el índice.
6 uq_compra_orden_compra único parcial
ON compra(id_orden_compra) WHERE id_orden_compra IS NOT NULL Una orden de compra no puede derivar en más de una compra — sin penalizar las compras directas, que no vienen de ninguna orden.

Regla de arquitectura del proyecto: los índices se crean para casos de uso identificados, no por anticipación genérica.
